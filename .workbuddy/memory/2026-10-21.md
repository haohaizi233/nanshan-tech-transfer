## 南山科转通 AI Agent 四阶段优化（续）

### 本轮新增（检索性能回归修复）

- **根因**：第二阶段把相关度下沉 SQL 后，检索 P95 从 12ms 涨到 145ms。
  定位过程分两层：
  1. EXPLAIN 显示相关度表达式与关键词条件各自重复拼接 5 个字段 → 每行约 30 次字符串拼接 + 25 次 ILIKE。
     修复：`WITH base AS MATERIALIZED` + 把 `status='published'` 等非关键词条件下推到 CTE 内部（先过滤再拼接）。
  2. 修复后仍慢 → 继续测发现**生产库 collation 是 `Chinese (Simplified)_China.936`（GBK）**，
     ILIKE 在 locale 感知比较下比 `COLLATE "C"` 慢 3.5 倍（8.50ms → 2.52ms）。
- **最终方案**：`taxonomy.SEARCH_COLLATION = "C"` + `taxonomy.collate()` 包装所有检索表达式
  （物化列、title、coop_mode、source_org_name、org_name_snapshot、region）。
- **正确性验证**：231+57 行 × 40 个词条 = **11520 个匹配格**逐格比对默认 collation 与 COLLATE "C"，
  **0 处差异**（`outputs/retrieval_collate_full_matrix.json`）。
- **延迟结果**（真实库，同一语料）：旧口径完整链路 P50 3.66ms / P95 4.85ms；
  新口径 P50 9.53ms / P95 12.76ms（回归前是 P50 10.7 / P95 108ms）。
  结论：性能已回到可接受区间，仍略慢于旧口径——这是"相关度排序取代 created_at 截断"的必要代价。
- **同时修复**：
  - `demand_service.py` 补上与 achievement 一致的 CTE 改造（原先两条路径行为不一致）。
  - 两个服务的 CTE/外层都改用显式列清单，`_searchable` 不再进入结果字典（服务层额外 pop 兜底）。
  - `advisor.grounded_explanation`：`analysis` 返回列表时被**静默丢弃** → 新增 `_normalize_analysis` 归一化。
  - `retrieval_quality.py` 延迟测量每口径只测 8 次（冷启动污染 P95）→ 改为预热 + 每关键词 15 次采样。
- **新增测试**：`tests/test_retrieval_quality.py`（28 个用例），把 SQL 结构契约
  （MATERIALIZED / 谓词下推 / COLLATE "C" / 参数顺序 / 内部列不外泄）与召回语义、
  重排投影、幻觉防护固化为可回归的断言。总测试数 89 → **117**。

### 经验备忘（后续同类优化直接套用）

1. PostgreSQL 上 ILIKE 慢，先查 `pg_database.datcollate`——非 C/UTF-8 collation 会走 locale 感知比较。
2. 相关度下沉 SQL 后必须配 `MATERIALIZED` CTE + 谓词下推，否则规划器把表达式下推回基表。
3. CTE 参数顺序 = CTE 内 WHERE → SELECT 里的表达式 → 外层 WHERE → LIMIT，顺序错了会静默取错值。
4. 延迟基准脚本必须预热 + 多次采样，单次采样会把冷启动算进 P95。

## 专利检索"搜索匹配算法"问题排查与修复（上游 vs 本地归因）

用户反馈两张企业微信截图：搜索"华为"显示"共 124922 件"；搜索"CN110086"返回葡萄酒专利
`CN1170923C`。用户明确要求：**"先排查下是上游的问题还是我们本地拿过来的问题"**。

### 归因结论（真实上游 `http://43.138.138.200:8081` 抓包证实，非推测）

| 现象 | 归因 | 证据 |
| --- | --- | --- |
| `CN110086` → 葡萄酒专利 `CN1170923C` | **上游** | 直连上游 `q=CN110086` 原样返回 `CN1170923C`，total=1，与截图逐字一致 |
| "共 124922 件" | **上游**（估算值）+ 本地分页契约缺陷 | total 按 125 分桶；"图像/模型/人工智能"三词 total 完全相同 124672；空 q 真实语料规模 101538 |
| 命中词无高亮 | **本地** | 上游返回 `<b>华为技术有限公司</b>`，本地 `clean_text` 剥掉标签 |
| 翻页会到空页 | **本地** | 本地 `page_meta` 用估算 total 算出 12493 页，上游 page=100 起返回空 |

### 上游匹配规则实测矩阵（关键产出）

上游 `/patent_search` 的 `q` 是 Google Patents 全文检索，**只在数字段长度恰好 7 位或 9 位时**
才当公开号做前缀匹配，其余长度退化为全文检索：

- `CN1100866`（7 位）→ 前缀匹配 ✓；`CN110086609`（9 位）→ 前缀匹配 ✓
- `CN110086`（6 位）→ **全文命中 ✗**（返回 `CN1170923C`）；`CN11008660`（8 位）→ **0 条 ✗**
- 原因：中国公开号两套号段体系（早期 7 位 / 2003 年后 9 位），上游只对这两种**完整**号段建了索引
- 其他国家（US/EP/WO）前缀匹配正常，不需要枚举
- `PN=` / `publication:` / `pub:` / `intext:` / `intitle:` 公开号字段语法上游均返回 0，不可用

### 上游限流实测（决定了枚举规模上限）

上游内部转发 Google Patents，吞吐约 2.8~7.5 req/s。并发 20~40 压测 100~200 次后，
上游持续返回 `{"detail":"search failed: HTTP Error 503: "}`（`/openapi.json` 仍 200，
是它的**后端**被打挂，非服务本身宕机），需等待其自行恢复（实测约 30 分钟）。
→ 100 候选（7→9 位补 2 位）16 并发耗时 12.5s，1000 候选（6→9 位补 3 位）同理不可行，
同步接口不可接受 → 枚举只做**补 1 位**（10 候选，约 1.2s）。

其他上游限制：`num` 上限 100（num=200 → 422）；`total_pages` 封顶 100。

### 经验备忘

1. 第三方接口出怪结果时，**先直连上游复现**再动本地代码——直连一致就是上游问题，
   否则才查本地引入。本次正是靠"直连上游返回 CN1170923C 与截图逐字一致"定性。
2. 编号类检索的通病：上游按"完整号段"建索引，短号段会退化成全文检索。
   兜底要用**严格前缀过滤**（杜绝误报）+ **受控枚举**（补召回），且枚举规模受上游吞吐约束。
3. 上游的 `total` 常是估算值（Google Patents 按 125 分桶），**不能用来算总页数**；
   要用上游自己的 `total_pages` 收敛，否则前端会翻到空页。
4. 压测第三方接口会打挂对方后端（本次 503 持续约 30 分钟）。压测前必须评估配额，
   或改用 mock + 低频探测。
5. 项目 Python 依赖在**仓库根**的 `.venv/Scripts/python.exe`（不在 tech-transfer-service 内）；
   前端测试用 `node --test "tests/*.test.mjs"`（路径需 glob，直接给目录会报模块找不到）。

### 补位枚举的并发超时（重要工程细节）

第一版超时保护有 bug：用 `as_completed` + 循环内检查 `deadline` 是**无效**的——
`as_completed` 本身会阻塞等下一个 future 完成，而且 `ThreadPoolExecutor` 的
`with` 块退出时会 `shutdown(wait=True)` 等所有卡住的线程结束，
实测上游完全卡死（sleep 30s）时仍然耗时 14~22s。

正确做法（三处都要改，缺一不可）：
1. `concurrent.futures.as_completed(futures, timeout=timeout)` —— 用它自身的 timeout，
   超时抛 `TimeoutError`（Python 3.11+ 与内置 `TimeoutError` 同一）；
2. 用 `pool = ThreadPoolExecutor(...)` 显式创建，`try/finally` 里
   `pool.shutdown(wait=False, cancel_futures=True)` —— **不能**用 `with` 块，
   否则退出时仍会等所有线程；
3. 单个候选抛异常只 `logger.warning` 跳过，不影响其余候选。

实测：上游完全卡死时，预算 1.0s → 1.02s 返回。
新增配置 `PATENT_ENUM_TIMEOUT`（默认 8.0 秒），写进 `config.py` 与 `.env.example`。
