## 一、性能排查方法论

### 核心原则

1. **先测量再优化**：不猜测瓶颈，用 curl/Chrome Network 实测数据定位
2. **区分链路层级**：本地直连 vs 公网 frp vs 浏览器渲染，逐层排除
3. **看请求总数而非单请求大小**：14-17s 慢加载的根因是 100+ 个 Vite 模块请求，不是单文件大
4. **TTFB vs Content Download**：Chrome Network 的总耗时 ≠ 服务器慢，可能是浏览器排队/JS 执行

### 测量工具

```bash
# 精确测量 TTFB / Total / 大小
curl -o /dev/null -w "ttfb=%{time_starttransfer}s total=%{time_total}s size=%{size_download}B" <URL>

# 本地 vs 公网对比
curl --noproxy '*' http://127.0.0.1:8787/h5/assets/xxx.js   # 本地
curl http://43.138.138.200:8077/h5/assets/xxx.js              # 公网(frp)

# 检查缓存头
curl -D- -o /dev/null <URL> | grep -i "cache-control\|etag\|content-encoding"

# 检查 Gzip 生效
curl -H "Accept-Encoding: gzip" -D- -o /dev/null <URL> | grep content-encoding
```

## 二、根因分析（三轮优化）

### 第一轮：Vite 开发服务器暴露到公网

| 项目 | 数据 |
|------|------|
| **症状** | 页面 14-17 秒加载 |
| **根因** | `/h5/` 路由优先代理到 Vite dev server(5173)，每个 .vue 组件/CSS/JS 模块都实时编译 |
| **证据** | HTML 包含 `<script src="/h5/@vite/client">`（105KB 热更新客户端） |
| **耗时链** | 100+ 模块 × (Vite 编译 2-10ms + frp 50ms) ≈ 14-17s |
| **修复** | 优先返回 `dist/build/h5/` 静态构建，Vite 仅做开发兜底 |

**教训**：不要把开发服务器暴露给公网用户。

### 第二轮：静态资源 404 + 缓存策略

| 项目 | 数据 |
|------|------|
| **症状** | Chrome 显示 index-C1wJNOJb.js 耗时 4.15s |
| **根因** | 旧 hash JS 文件不存在 → 兜底返回 HTML → JS 解析报错 → 白屏 |
| **证据** | `curl /h5/assets/index-C1wJNOJb.js` 返回 `<!DOCTYPE html>` 而非 404 |
| **修复** | 带扩展名文件不存在返回 404；hash 资源加 `immutable` 长缓存 |

**教训**：SPA 路由兜底只应作用于路由路径（无扩展名），不应兜底静态资源。

### 第三轮：图片体积 + 加载时机

| 项目 | 数据 |
|------|------|
| **症状** | 图片 2-2.4s 加载完成 |
| **根因** | ①图片在 JS 执行后才发起请求 ②单图 164KB（实际显示 414px，图片 1200px） |
| **证据** | curl 单图 109ms（下载不慢），但 Chrome 2.34s（排队等 JS） |
| **修复** | 压缩图片(-71%) + preload fetchpriority=high + StaticFiles 直发 |

**教训**：图片 2.34s ≠ 网络慢。要区分"下载耗时"和"请求发起时机"。

## 三、优化清单

### 架构层

| 优化 | 前 | 后 | 效果 |
|------|------|------|------|
| H5 资源服务 | Vite dev 代理 | 静态构建 + StaticFiles | 14-17s → <2s |
| GZip 压缩 | 无 | GZipMiddleware | 30KB → 4.7KB (-85%) |

## 四、关键技术点

### 1. uni-app H5 构建模式判断

```bash
# 看 HTML 包含什么就知道是 dev 还是 prod
curl http://127.0.0.1:8787/h5/ | head -5
# dev: <script src="/h5/@vite/client">
# prod: <link href="/h5/assets/uni.xxx.css">
```

### 2. 静态资源缓存策略

```
HTML:     Cache-Control: no-cache          (每次刷新拿最新 hash 引用)
hash资源: Cache-Control: immutable, 1年    (文件名含内容 hash，内容变名字就变)
static/:  Cache-Control: no-cache 或短缓存 (无 hash 的资源)
```

### 3. SPA 路由兜底规则

```python
# 正确：只兜底路由，不兜底资源
if "." in filename:  # 带扩展名 = 静态资源
    return 404 if not exists
else:                # 无扩展名 = SPA 路由
    return index.html
```

### 4. 图片压缩工具

```bash
# macOS sips
sips -Z 128 input.png --out output.png             # 缩放到 128px
sips -s format jpeg -s formatOptions 70 input.png   # 转 JPG q70
sips -g pixelWidth -g pixelHeight image.png         # 查看尺寸

# 原则：图标 ≤96px，背景图 ≤750px，照片 JPG q70-q75
```

### 5. 首屏 LCP 图片加速

```html
<!-- HTML 中 preload 首屏关键图片 -->
<link rel="preload" as="image" href="/h5/assets/banner-xxx.jpg" fetchpriority="high">
```

### 6. GZip 中间件

```python
from fastapi.middleware.gzip import GZipMiddleware
app.add_middleware(GZipMiddleware, minimum_size=512, compresslevel=6)
```

## 五、排查陷阱

| 陷阱 | 正确做法 |
|------|----------|
| 用 API 健康检查证明前端没问题 | 分别测量前端资源和 API |
| 把 Chrome 总耗时当服务器慢 | 区分 Queueing/TTFB/Download/Parse |
| 看文件小就忽略 | 100+ 个小文件 × 50ms = 5s |
| GZip 压缩率高=页面快 | 压缩减少传输，但不解决请求排队 |
| 图片加载慢=网络差 | 可能是 JS 执行后才发起请求 |
| 直接引入 CDN | 先证明确实是网络瓶颈再上 CDN |
