# ADR-003 · 模块化单体而非微服务群（Modular Monolith）

> 状态：已冻结（Frozen，2026-09-02 冻结评审通过，决议见 10-freeze-review.md；此后只增不改）
> 日期：2026-09-02
> 决策人：科转通架构组
> 影响范围：后端部署形态、模块边界、事务与集成方式

---

## 1. 背景与问题

科转通后端 `tech-transfer-service` 是一个独立可部署单元，对上级 Ai南山 平台而言可被称为"一个微服务"。于是出现诱惑：内部是否也按领域拆成用户服务、成果服务、需求服务、对接服务、AI 服务等多个网络微服务？

当前事实基线（依据 `01-current-state-audit.md`）：

- 业务数据规模：成果约 223 条（需求方陈述，数据文件待补）、需求/成果演示数据各 3 条、资本资源 137 条；
- 用户量：一期无公开用户，试点期预估数百级；
- 团队规模：前端 1 + 后端 1 + 兼职数据/AI 的小团队；
- 领域关系：需求 ↔ 成果 ↔ 对接 ↔ 收藏之间事务关系密集（对接意向要同时校验需求状态、成果状态、双方身份，单库单事务即可保证一致性）。

## 2. 决策

`tech-transfer-service` 内部采用**模块化单体（Modular Monolith）**：

1. **一个进程、一个数据库 schema、一套部署流水线**；
2. 内部划分 15 个模块（identity / profile / organization / achievement / demand / favorite / cooperation / search / ai / patent / capital / notification / audit / admin / file），模块间**单向依赖、禁止环**（依赖图见 02 §7）；
3. 模块边界用**代码组织 + import 约定 + 评审规则**强制，而不是用网络边界强制；
4. 跨模块写操作通过模块间函数调用共享同一数据库事务；模块对外能力一律通过 REST 接口层暴露；
5. 对外部的 AI 能力、专利 SaaS、上传、通知，通过**进程内 Provider 接口**适配（`AiProvider` / `PatentProvider` / `UploadProvider` / `NotifyProvider`），密钥只存在于服务端配置。

## 3. 为什么不拆微服务（逐条）

| 拆分收益 | 当前实际情况 | 结论 |
|----------|--------------|------|
| 独立扩容 | 无流量热点；AI 调用量一期极小 | 不成立 |
| 团队自治 | 后端 1 人，无多团队协作边界 | 不成立 |
| 技术异构 | 全部可用同一栈实现 | 不成立 |
| 故障隔离 | 拆分反而引入网络失败面（超时、重试、分布式事务） | 负收益 |
| 数据所有权清晰 | 单库 schema 内按模块划分表已足够 | 已满足 |

拆分的**真实成本**：网关路由配置、服务注册发现、链路追踪、跨服务分布式事务（对接意向的创建涉及需求方+成果方双侧校验）、双倍部署与监控负担——每一项都由"1 个后端"承担。

## 4. 演进触发条件（何时重审本 ADR）

满足以下任一条时，重审并考虑把对应模块拆出：

| 触发条件 | 拆什么 |
|----------|--------|
| AI 任务日量 > 1 万 或 需要独立 GPU 资源池 | `ai` 模块 → 独立推理服务（任务表 + 回调） |
| 成果/需求数据 > 5 万条 或 搜索 P95 > 500ms | `search` → 引入 Elasticsearch（先于拆服务） |
| 科转通团队后端 > 5 人且出现并行发布冲突 | 按团队边界重新评估 |
| 上级平台强制要求服务注册/网格接入 | 按 08 清单 C-07 与上级协商 |

未触发前，**禁止"预防性"引入** Kubernetes、服务网格、Kafka、ES 集群、独立向量库（依据 02 §9 基础设施决策表）。

## 5. 模块边界执行机制

1. **目录即边界**：`modules/<name>/` 内含 router / service / repository / models，模块间只允许 import 对方 `service.py` 暴露的门面函数，禁止跨模块 import repository 或 ORM 对象；
2. **评审清单**：PR 涉及跨模块 import 时逐条检查依赖方向（对照 02 §7 依赖图）；
3. **自动化护栏**：CI 脚本静态扫描 import 语句，发现反向依赖（如 achievement → cooperation）即失败；
4. **事务边界**：每个用例一个事务；跨模块组合用例（如"创建对接意向"）由 cooperation 模块编排，内部调用 demand/achievement 的校验门面，同一事务提交。

## 6. 后果

**正面：** 一条事务保证对接全流程一致性；部署/调试/回滚都是单单元；小团队可维护。

**负面与代价：** 模块边界靠纪律与评审维持，存在"顺手跨模块查表"的腐化风险（以 §5.3 自动化护栏缓解）；未来拆分时需要补做服务间契约（但 REST 层已是天然契约，拆分成本可控）。
