## 2. 逐项明细

### C-01 宿主身份凭证格式

- **需谁确认**：Ai南山 后端负责人。
- **为什么**：`POST /auth/bootstrap` 的 `hostCredential` 与 `AiNanshanIdentityProvider` 验签逻辑依赖上级 token 的格式（JWT？ opaque？ 一次性票据？）、签名密钥、过期策略。
- **默认方案**：本地模式已实现票据协议 `local-dev-ticket-<subject>`；正式模式预留 opaque token 直传上级验签接口的适配位（IdentityProvider 接口不变）。
- **不确认影响**：AiNanshanIdentityProvider 无法实现，正式环境无法登录；不影响本地全链路开发。
- **最晚阶段**：阶段 D 开始时（合并上级源码当天必须拿到，否则阶段 D 阻塞）。

### C-02 上级用户资料字段范围

- **需谁确认**：Ai南山 产品 + 后端。
- **为什么**：决定科转通 user_profile 是否需要从上级同步 displayName/手机号，还是完全由用户在科转通侧自填。
- **默认方案**：**科转通只存用户主动填写的资料，不自动同步上级资料**（上级身份仅用于认证映射，ADR-002 §4）。姓名空显示"未填写"。
- **不确认影响**：无阻塞；若上级要求资料同步，需增加一个资料拉取 Provider 与字段映射（约 2 人日，不影响表结构）。
- **最晚阶段**：阶段 D 初。

### C-03 网关身份传递方式

- **需谁确认**：Ai南山 网关/后端负责人。
- **为什么**：上级网关验签后，以什么形式向下游服务传递可信身份（透传原 token？ 注入 `X-User-Id` 类可信头？ 网关签发内部 token？）决定 AiNanshanIdentityProvider 解析入口与防伪造策略。
- **默认方案**：上级 token 原样透传（Authorization 头），科转通自行验签。**若采用可信头方案，科转通服务必须仅接受网关内网来源请求（网络隔离或 mTLS），防止外部伪造可信头**——此为安全关键分叉。
- **不确认影响**：正式身份链路无法定稿；本地开发不受影响。
- **最晚阶段**：阶段 D 初（与 C-01 同时）。

### C-04 统一上传通道规范

- **需谁确认**：Ai南山 后端/基础设施。
- **为什么**：UploadProvider 正式实现：用上级统一上传接口，还是科转通自建对象存储。决定 `presign` 返回的 uploadUrl 指向。
- **默认方案**：科转通自建对象存储预签名直传（响应结构 UploadPresignResult 不变）；上级如有统一通道，仅替换 Provider 实现。
- **不确认影响**：附件功能可正常上线（自建方案完整）；上级若强制统一通道则需重写 Provider（1–2 人日）。
- **最晚阶段**：阶段 D 中（附件功能联调前）。

### C-05 企业/机构体系对接

- **需谁确认**：Ai南山 产品。
- **为什么**：上级若有企业认证/成员体系，科转通 organization 应映射而非自建；若无，保持自建主数据。
- **默认方案**：科转通自建 `organization` 表（05 §2.4），不与上级机构体系耦合。
- **不确认影响**：无阻塞；若上级要求对接，需增加机构映射表（影响中等，业务表 org_id 结构不变）。
- **最晚阶段**：阶段 D 中。

### C-06 消息通知通道规范

- **需谁确认**：Ai南山 消息平台负责人。
- **为什么**：NotifyProvider 正式实现：对接上级小程序订阅消息/站内信 API 的凭证、模板、频控。
- **默认方案**：降级为科转通站内 notification 表（已在设计内），对接审批通过前通知不出科转通边界。
- **不确认影响**：用户在上级小程序内收不到对接/审核提醒（体验受损，主链路不受损）。
- **最晚阶段**：阶段 D 中。

### C-07 服务注册/网关接入与部署资源

- **需谁确认**：Ai南山 基础设施负责人。
- **为什么**：tech-transfer-service 的部署形态：虚机/容器？是否必须接入上级服务注册体系（Nacos/K8s）？网关路由 `/api/tech-transfer/v1/*` 由谁配置？
- **默认方案**：独立部署单元 + 网关路径路由（无需服务注册）；不引入 K8s（02 §9 决策）。
- **不确认影响**：staging 联调环境无法搭建；本地不受影响。
- **最晚阶段**：阶段 D 初。

### C-08 上级小程序源码与分包合并方式

- **需谁确认**：Ai南山 前端负责人。
- **为什么**：合并方式（git 仓库策略：fork？ subtree？ 直接目录复制）、pages.json 合并规则、静态资源路径前缀、分包大小预算。
- **默认方案**：subtree/目录复制合并 `subpackages/tech-transfer/`，pages.json 由上级侧注册分包（03 §7）；分包体积预算按微信 2MB 分包上限预留 1.5MB。
- **不确认影响**：阶段 D 无法启动；本地开发不受影响。
- **最晚阶段**：阶段 D 初（**本项目当前最大外部依赖**）。

### C-09 发布/审核流程（微信平台侧）

- **需谁确认**：Ai南山 项目管理。
- **为什么**：科转通功能随上级小程序发版，需知道发版节奏、体验版/审核版流程、回滚责任边界。
- **默认方案**：科转通功能合入上级 main 分支后随上级既定节奏发版；科转通侧只保证分包回归绿。
- **不确认影响**：上线时间不可控，不影响开发。
- **最晚阶段**：阶段 D 末（上线前）。

### C-10 数据库资源供给方式

- **需谁确认**：Ai南山 基础设施。
- **为什么**：tech_transfer schema 部署在上级 MySQL 实例（共用实例独立 schema）还是科转通自购实例；备份与权限策略。
- **默认方案**：优先自建/独享实例；若共用实例，坚持**独立 schema + 独立账号（禁 root、禁跨库写）**（02 §11.2 硬约束）。
- **不确认影响**：staging/生产库无法创建；本地开发用本机 MySQL 不受影响。
- **最晚阶段**：阶段 D 初。

### C-11 埋点与错误上报规范

- **需谁确认**：Ai南山 数据/前端负责人。
- **为什么**：HostBridge.reportError 上报到上级监控还是科转通日志。
- **默认方案**：先落科转通服务端日志（external_api_log / 应用日志），后接上级体系。
- **不确认影响**：仅监控可见性，不影响功能。
- **最晚阶段**：阶段 D 中。

### C-12 tenant 多租户需求

- **需谁确认**：Ai南山 产品 + 后端。
- **为什么**：Ai南山 是否存在多租户（多区域/多主体）运营规划，决定 external_identity.tenant_id 是否必须承载真实租户值。
- **默认方案**：`tenant_id='default'` 单租户（唯一约束已含该列，未来直接填真实值即可，无迁移成本——ADR-002 设计即为此预留）。
- **不确认影响**：无（表结构已兼容两种结论）。
- **最晚阶段**：阶段 D 初。
