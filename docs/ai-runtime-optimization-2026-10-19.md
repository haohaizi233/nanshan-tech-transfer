## 发现与落实

| 维度 | 原问题 | 本轮处理 |
| --- | --- | --- |
| 动态数据 | AI 卡片是历史快照，没有实时浏览次数展示；从缓存进入成果详情不会记录新的访问 | 卡片展示 `viewCount`；新增认证的批量只读统计接口；成果详情每次进入后台读取最新详情并记录访问，同时保留已有内容 |
| 统计副作用 | 用详情接口刷新数字会把轮询当成访问 | 统计接口只查 `view_count`，每批最多 50 个目标、最多两次查询；前端对全部可见卡片去重后顺序分批，只返回未删除的已发布内容，不做 UPDATE |
| 前端生命周期 | 历史消息不应因统计变化反复改写；隐藏页面不应继续查询 | 数字放在独立的 `cardViewCounts`；返回页面、新消息出现时刷新，页面停留时每 15 秒校验；隐藏/销毁停止，晚到及跨账号结果丢弃 |
| 超时预算 | 主服务每次重试重新拿完整超时；模型层备用预算没有在每次尝试和退避时执行 | 主服务队列等待、转发及退避共享截止时间，并向 agent 传递剩余预算；agent 只接受缩短，不能借请求头扩展服务上限；模型重试/备用调用继续受同一预算约束 |
| 并发容量 | HTTP 超时后工作线程仍执行，但信号量已释放，后续任务继续排入线程池 | 槽位由真实工作 Future 的结束回调归还；提交失败及排队取消也有释放路径；超时不会冒充线程已停止 |
| 模型开销 | 重排只截断简介，创新点及应用字段的嵌套结构仍可能撑大请求 | 对字符串、数组、嵌套深度及整个请求限制大小；默认最多 24000 字符，预算不足或候选太少时保留本地排序 |
| 响应容错 | 重排列表混入 null/数字会在异常保护之外报错；模型可能引用未进入上下文的 ID | 跳过非对象、未知及重复 ID；只接受实际送入该次模型上下文的候选；失败时继续使用真实检索结果 |
| 失败分类 | 400 等非瞬时错误也可能触发备用模型 | 非可重试 HTTP 错误立即返回，不重复消耗备用额度；502/503/504/429 和网络错误仍按受限策略处理 |
| 观测 | 难以关联业务请求与多次模型调用 | 转发并校验 `X-Request-Id`；路由、检索、重排、模型及整轮记录耗时与结果；已有 LLM 诊断事件增加同一 trace ID |

新增阶段日志只包含 trace ID、阶段、耗时、结果，不输出提示或工具正文。原有详细 LLM 日志策略没有在本轮整体替换，因此不声称整个系统已经默认关闭内容日志。

## 参数与接口

- 新接口：`POST /api/tech-transfer/v1/ai/cards/view-counts`，请求 `{"cards":[{"card_type":"achievement","id":42}]}`，返回 `data.list` 中相同类型/ID 的 `viewCount`。
- `AI_RERANK_MAX_CHARS`：默认 24000，启动校验范围 4000—64000。降低该值可能减少参与模型重排的候选；不会制造新候选。
- `X-AI-Timeout-Seconds`：内部可选请求头，传递剩余时间；无效值回退服务配置，大于服务上限时仍受服务上限限制。
- 不改变现有 `/ai/chat` 请求体、聊天轮次 ID、结果持久化、WAL 和账号隔离约定。
- 原始网络请求/数据库驱动仍有自己的超时语义。到期能够阻止后续尝试，不意味着 Python 可以强杀已经运行的线程；容量会保持占用直到线程真正结束。

## 验证

## 后续能力分期

以下需要单独的数据与验收设计，不包装成本轮已经完成的能力：

1. 多轮指代、追问及“第一个更便宜的”等会话上下文，需要把可信业务历史与当前输入分开传入。
2. 硬条件/软偏好分离、混合召回和语义相关度，应先建立带标注的真实查询集，再做 A/B 评测。
3. 长期记忆、跨代理协作、工具写操作需要独立的权限、租户隔离与生命周期，不能靠提示词替代代码授权。
4. 更完整的隐私日志策略、端到端流式进度和外部监控接入需要明确保留策略及运维环境，本轮不新增外部日志接收端。

部署需要同时更新主服务、AI 服务和前端，并重启后端进程；仅推送 Git 不等于生产服务已经重启。
