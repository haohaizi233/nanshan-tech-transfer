# 统一通知与待办收件箱设计

## 目标

为后台管理端和小程序端提供统一、持久化的未读通知能力。高频刷新只更新角标摘要；进入实际业务页后才加载详情并消费对应未读。

## 范围

### 后台管理端

- 数据概览的待办按 `occurred_at DESC, id DESC` 排序，最多返回 100 条，列表容器可独立滚动。
- 顶部铃铛显示全部未读总数；左侧导航显示各业务类别待办数：内容审核、合作对接、机构入驻、成员入驻。
- 每 200ms 仅刷新摘要；不轮询 `summary`、趋势、待办正文或任一管理列表。

### 小程序端

- 应用处于前台时，每 200ms 仅请求当前用户的未读摘要，并用 `uni.setTabBarBadge` 更新“我的”页角标；为防止无界显示，99 以上显示 `99+`。
- 处于后台、隐藏或请求尚未返回时不发起下一次请求。
- 进入“我的发布”“意向请求”“机构申请/成员申请”页时，先按原逻辑加载完整业务数据；加载成功后标记相应类别已读，再立即刷新角标。

## 数据模型

新增 `notification_inbox`：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `recipient_user_id` | 收件人 |
| `category` | `review`、`cooperation`、`organization`、`membership` |
| `event_type` | 例如 `achievement.approved`、`cooperation.accepted` |
| `source_type`、`source_id` | 业务对象定位 |
| `title`、`body`、`target_path` | 可展示文案与跳转位置 |
| `occurred_at` | 业务事件发生时间 |
| `read_at` | NULL 即未读 |
| `dedupe_key` | 唯一键，防止重试/轮询导致重复通知 |

通知写入必须与原业务状态流转使用同一个数据库事务；写入失败使状态流转整体失败，避免“状态已变、用户却无提醒”。

## 事件与收件人

| 事件 | 收件人 | 分类 |
| --- | --- | --- |
| 需求/成果审核通过、拒绝 | 内容所有者 | `review` |
| 收到对接申请 | 目标内容所有者 | `cooperation` |
| 对接同意、拒绝、确认、完成、取消 | 意向的另一方 | `cooperation` |
| 机构入驻申请待审核/审核结果 | 平台管理员/申请人 | `organization` |
| 成员入驻或管理员申请待处理/审核结果 | 机构管理员/申请人 | `membership` |

平台协助对接中，目标无平台账号时不向虚拟目标方投递；发起方收到平台处理的接受、拒绝等状态通知。

## 接口

- `GET /me/notifications/summary`：返回 `{ total, categories }`；只含数字。
- `POST /me/notifications/read`：body 为 `{ category }`，将该收件人的该类别未读记录标为已读。
- `GET /admin/notifications/summary`：返回后台左侧导航与铃铛所需的类别统计；管理员待办计数由未完成业务项实时聚合，不污染普通用户收件箱。
- 既有 `GET /admin/dashboard/todos?limit=` 改为最新在前，并保留完整待办数据只供概览页首次加载或人工刷新。

## 刷新与性能

客户端建立单例轮询器，固定 200ms 调度但同一时刻最多一条摘要请求；网络错误采用一次调度后重试，不清空最后一次成功角标。轮询被生命周期暂停后不补发历史请求。响应只返回几个整数，不能读取业务详情、联系人或大列表。

## 安全与未读语义

普通用户只能读取、消费自己的收件箱；管理员接口由现有 `admin_identity` 保护。只有成功加载相关业务页后才标记已读，访问其它页面、刷新角标及轮询均不消费未读。

## 验收

- 新事件在 200ms 轮询周期内改变对应角标，但不触发详情列表请求。
- 后台待办最新在前、可滚动，并且左侧和铃铛数量一致。
- 小程序退到后台后停止轮询；回来后立即刷新一次。
- 审核、对接、机构和成员流程均有去重通知，点击/进入对应页后只清除该类别已读数。
